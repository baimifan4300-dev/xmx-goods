# 架构设计与迁移方案（V4 → V5）

> 基线：`xmx-goods-site/xmx-goods-v2-preview`（V4，1537 条商品、20 主分类、联动/满赠本地分类管理）。
> 本次目标：在不回退 V3/V4、不覆盖现有数据的前提下，把静态站点升级为 Supabase 云端版。

---

## 一、V4 审计结论

| 项目 | V4 现状 | V5 处理 |
|---|---|---|
| 页面 | 首页/全图鉴/收藏/愿望/进度 + 商品详情弹窗 | 全部保留，新增登录、账户/数据、商品编辑、图片管理弹窗 |
| 商品 | `data/gyly/xmx/products.json` 1537 条，原始字段完整 | 不修改 JSON；登录后按用户导入 `products`，`payload` 保存全字段 |

## 二、架构选择

### 2.1 静态前端 + BaaS

- 前端继续用原生 HTML/CSS/JS，Vercel 静态部署；不引入服务器运行时。
- Supabase 提供 Auth/PostgreSQL/Storage/Realtime；`@supabase/supabase-js` 由 esbuild 打包进 `app.js`。
- `config.js` 运行时配置只放 anon public key；构建时可由 Vercel 环境变量生成。

### 2.2 数据隔离模型

**每个用户拥有自己的一份完整图鉴**（包括 1537 条原始商品的副本）。

原因：
1. 用户可编辑/删除原始商品，若共享全局商品表，会影响其他用户；
2. RLS 简单：所有私人表 `owner_id = auth.uid()`；
3. 备份/恢复/迁移到新账号不需要做“全局商品 + 用户覆盖层”的复杂合并；
4. 单人使用场景下存储成本可忽略（1537 行 JSONB 约 2MB）。

代价：多用户时商品数据重复；本项目是个人收藏站，接受该取舍。

### 2.3 云端权威 + 本地只做预览

- 云模式：登录后从 Supabase 加载；不把 localStorage 当权威数据源；不写“本地优先”的云端替代。
- 本地预览：只有显式 `?demo=1`（或 `demoFallback: true`）才使用 `LocalBackend`，页面明确标注“本地预览、不会跨设备同步”。
- 本地预览用于开发/演示和 E2E，不会在已配置 Supabase 的正式入口悄悄启用。

## 三、数据库设计

完整 SQL 见 `supabase/migrations/`。

### 3.1 表

| 表 | 主键 | 说明 |
|---|---|---|
| `profiles` | `id` | 用户资料，auth.users 触发器创建 |
| `works` | `id` | 作品（gyly） |
| `characters` | `(work_id,id)` | 角色（xmx） |
| `main_categories` | `key` | 20 个固定主分类，公开只读 |
| `products` | `(owner_id,id)` | 商品；`payload` 完整 JSON；列字段用于索引/同步 |
| `collections` | `(owner_id,product_id)` | 收藏；数量/购买价/日期/备注 |
| `wishlist` | `(owner_id,product_id)` | 愿望 |
| `board_categories` | `(owner_id,id)` | 联动/满赠分类；保留 V4 ID |
| `board_assignments` | `(owner_id,product_id,board_key)` | 商品→子分类；无记录=未分类 |
| `product_images` | `id` | 上传图片元数据；唯一 `(owner,product,kind)` |
| `user_settings` | `owner_id` | 迁移标记、默认分类初始化、上次备份时间 |
| `backup_logs` | `id` | 导出记录（可选） |

### 3.2 关键字段与约束

- `products.market_price` 独立于 `collections.purchase_price`。
- `collections.quantity >= 1`。
- `board_key in ('collab','gift')`。
- `board_categories.name` 长度 1–20；同用户同板块同名唯一。
- `board_assignments` 外键：
  - 商品删除 → 级联删除归属；
  - 分类删除 → 级联删除归属，商品保留。
- `products.work_id/character_id` 外键到 `characters`。
- 所有可编辑表有 `revision`，触发器 `bump_revision` 在更新时 `revision = old.revision + 1`。
- `board_assignments` 触发器校验商品/分类属于同一板块。
- `products.payload` 不存 `_revision`，避免内部版本字段污染原始数据。

### 3.3 RLS

- 所有私人表：`select/insert/update/delete` 均要求 `auth.uid() = owner_id`。
- `works`/`characters`/`main_categories`：公开只读。
- `profiles`：仅本人。
- Storage `product-images`：private；`select/insert/update/delete` 约束路径第一段 = `auth.uid()::text`。
- 没有前端 service_role；SQL 中没有 `bypassrls`。

### 3.4 Realtime

- `products, collections, wishlist, board_categories, board_assignments, product_images` 加入 `supabase_realtime` publication（幂等 DO 块）。
- 前端订阅 `postgres_changes`，按 `owner_id` 过滤；收到后 debounce 刷新。
- Realtime 失败时仍可通过窗口聚焦/可见性/手动同步刷新。

## 四、同步与冲突

### 4.1 读取

1. 登录后 `loadSnapshot()` 并行拉取所有表；
2. 商品分页 1000 条（1537 需两页）；
3. 组装 `store`，生成图片签名 URL（Storage 私有桶，1 小时）；
4. 渲染页面。

### 4.2 写入

- 新增：`insert`，ID 由客户生成（`U-...`），数据库 `(owner,id)` 唯一。
- 修改：`update ... where owner_id = ? and id = ? and revision = ?`；返回 0 行即冲突。
- 删除：`delete ... where revision = ?`；返回 0 行即冲突/已删除。
- 分类/收藏/图片同样使用 `revision`。
- 冲突时拉取当前云端记录，弹窗对比字段，用户选择：
  - 保留云端版本；
  - 用我的版本覆盖（以最新 revision 再写一次）。
- 不静默 last-write-wins。

### 4.3 多设备

- 同账号所有设备读同一份云端数据。
- 修改后其他设备：Realtime 推送（若开启）；否则刷新/重新进入/窗口聚焦时拉取。
- 图片上传后其他设备通过 Storage 签名 URL 读取。

## 五、图片方案

- 私有桶 `product-images`，路径 `${userId}/${productId}/${kind}-${timestamp}.${ext}`。
- `kind = cover`（无合集图的新商品封面）或 `highres`（在原合集图之外的高清独立图）。
- 上传：
  1. 前端校验类型/大小/尺寸；
  2. 大图压缩到最长边 2400px、质量 0.9；
  3. 生成 640px WebP 缩略图；
  4. 上传主图 + 缩略图；
  5. 写 `product_images`；替换时删除旧文件。
- 展示：
  - 卡片优先缩略图；
  - 详情有“高清图/合集定位”切换；
  - 删除高清图后回到原合集图红框；无合集图则占位。
- 备份时下载所有上传图 + 原始合集图/缩略图，写 SHA-256 清单。

## 六、迁移方案

### 6.1 迁移前

- V4 的 `products.json`、`assets/` 原样保留。
- 首次云端迁移前自动下载 `xmx-v4-premigration-*.json`（含 V4 本机收藏/分类/内置商品数据）。
- 不删除任何 V4 localStorage 键。

### 6.2 首次导入（云端 products = 0）

1. 读取 `data/gyly/xmx/products.json`（1537）；
2. 读取 V4 `xmx.collection.v1`、`xmx.boards.v1.gyly.xmx`、旧商品键；
3. 分批 upsert 商品（`ignoreDuplicates`，可重复执行）；
4. 迁移分类（保留 ID/顺序）；无本地分类时创建默认满赠四类；
5. 迁移归属；按云端实际分类 ID 映射，避免外键失败；
6. 迁移收藏（qty 默认 1，price→purchase_price，date/note）；
7. 迁移愿望；
8. 写 `user_settings.migration` + `defaultsInitialized`；
9. 标记本机已迁移（仅标记，不删数据）。

### 6.3 合并（云端已有数据）

- 不重新导入 1537 条基础商品；
- 只补充本机自定义商品、收藏、愿望、分类与归属；
- 全部按唯一键 upsert，不覆盖已有购买价；
- 同名分类冲突时保留云端分类，归属按名称映射；
- 可在账户里重复执行，不会重复。

### 6.4 迁移后验证

- 1537 总数；
- 20 主分类顺序；
- 收藏/愿望数量；
- 联动/满赠分类、归属；
- 图片路径与红框；
- 新增/编辑/删除/备份恢复。

## 七、备份格式

```text
xmx-goods-backup-YYYYMMDD-HHmmss.zip
├── manifest.json     格式/版本/导出时间/计数/图片清单/SHA-256
├── data.json         商品、收藏、愿望、分类、归属、图片元数据、设置
├── README.txt        说明
└── images/
    ├── uploads/      用户高清图与缩略图
    └── base/         原始合集图与裁切缩略图
```

- `format: xmx-goods-backup`, `formatVersion: 2`, `schemaVersion: 2026-11-supabase-v1`。
- 恢复前校验格式/版本/图片存在/SHA-256。
- 两种模式：
  - 合并（推荐）：只补充缺失，不覆盖已有；
  - 覆盖同 ID：用备份覆盖云端同 ID 记录。
- 恢复前两次确认（第二次输入“恢复”）。
- 恢复报告列明导入/跳过/失败/警告，可下载 txt。
- 避免重复：按 `(owner,id)` / `(owner,product_id)` / `(owner,product,kind)` 唯一键 upsert。

## 九、风险与取舍

| 风险 | 应对 |
|---|---|
| 真实 Supabase 未在本环境联调 | 提供 SQL/PGlite 测试、本地 E2E；部署后按验收清单做一次线上验收 |
| 首次导入 1537 条较慢 | 分批 200 条、进度提示、可重试、幂等 |
| 多设备冲突 | revision 乐观锁 + 冲突弹窗，不静默覆盖 |
| 私有图片签名 URL 过期 | 聚焦/刷新重新签名；失败回退合集图 |
| 备份体积大（约 41–55MB） | 可选择不含原始合集图；上传图始终包含；压缩/进度提示 |
| 手机内存不足 | 备份默认包含原始图，手机可取消“包含原始合集图” |
| 删除原始商品误操作 | 二次确认 + 输入“删除” + 建议先备份 |
| 浏览器拦截自动迁移快照下载 | 本机数据不删除；账户内可手动导出收藏 JSON |
| 免费 Supabase 项目暂停 | 文档说明；恢复项目后数据仍在 |
