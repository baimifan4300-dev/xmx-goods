# 06 · 风险清单与待确认事项

## 1. 高风险（会影响数据/架构，必须先确认）

| # | 风险 | 影响 | 缓解方案 | 阶段 |
|---:|---|---|---|---|
| R1 | 书籍模型选错：把一套书当一个商品 | 无法逐卷记录价格/版本/状态，后期返工 | 采用 `book_sets` + `books`（每卷/独立书一行），不塞进 `products` | P1/P3 |
| R2 | 付款只存「已付总额」 | 分批付款/退款/运费会重复或漏算 | 只存 `payment_records` 流水，`balance_due` 由视图计算 | P1/P4 |
| R3 | 软删除与现有 `ON DELETE CASCADE` 冲突 | 永久删除父记录会级联删子记录 | 软删除只 update `deleted_at`；永久删除从回收站按依赖顺序执行并二次确认 | P1/P6 |
| R4 | 自定义主分类删除 | 商品 `main_category_key` 变悬空 | 删除前查商品数，必须重归类/未分类；软删除可恢复 | P2 |
| R5 | `works/characters` 加 owner 字段 | 现有 1537 商品外键可能受影响 | 只加 nullable 列，不改 PK/FK；内置行 `owner_id=null,is_builtin=true` | P1/P2 |
| R6 | 备份体积膨胀（多图/徽章） | 手机备份失败/超时 | 图片 STORE 不压缩、进度条、可选原始图、后续分卷 | P6 |
| R7 | 自定义字段全表扫描 | 搜索变慢 | 1537+书籍规模小，先客户端过滤；后续加 GIN/trigram | P5 |

| R9 | 多设备同时付款/改状态 | 金额/状态覆盖 | 所有新表 `revision` 乐观锁；流水只追加不覆盖 | P1/P4 |
| R10 | Migration 在线上执行失败 | 表/策略半成品 | 先在测试项目演练；每份文件幂等；失败只回滚新增表；执行前完整备份 | P1 |
| R11 | Supabase Storage 限额/费用 | 图片/备份上传失败 | 12MB 限制、压缩、私有桶、备份前提示体积；监控使用量 | P6 |
| R12 | 单文件 `main.js` 2608 行 | 新功能继续堆叠会难维护 | P1 起按模块拆 `src/v6/*`，不一次性重写 V5 | P1–P6 |

## 3. 低风险/已知限制

- 当前 Supabase 项目只有 1 个用户、1 个作品、1 个角色；V6 多作品/角色没有真实数据可回归，需要测试数据。
- 线上私有表行数没有在 P0 直接读取；P1 前建议用只读 SQL 核对。
- 1537 条中 435 条无主分类、1527 条无系列；V6 不能假设都有分类/系列。
- `products.series` 只有 8 种非空值；自动建系列只覆盖这些，其余需手动。
- 现有 `product_images` 只有 cover/highres；多图相册需要新表 + 回填镜像。
- 现有 `wishlist` 没有目标价/链接/店铺；迁移后这些字段为空，需你补录。
- 报告需要历史状态；没有 `status_history` 时，只能用当前状态 + 购买日期近似。
- 单用户场景下 `works/characters/main_categories` 允许 authenticated 编辑；如果未来开放注册，需要改为 owner override。
- Supabase 免费/低配项目的 Storage/带宽/备份可能不足；大量多图相册前要评估。
- 所有 Migration 需要你在 Supabase SQL Editor 执行；我没有数据库密码/service_role，不能代跑。
- V6 前端会显著变大；需要拆模块，否则 `main.js` 会继续膨胀。

## 4. 需要你确认的 8 个设计点

### Q1. 书籍「一卷一行」是否接受？

建议：`books` 一行 = 一个独立书/一卷书；同卷多本用 `quantity`，不同副本价格用订单行。
影响：如果要求「同一卷 3 本分别记录买入价」，需要再加 `book_copies` 表，P3 会增加约 2–3 人天。

### Q2. 套书必须属于系列吗？

你的补充要求：**不强制**。设计已支持 `book_sets.series_id` 可空；独立单本 `set_id` 可空。
确认：套书可以完全不属于任何系列，对吗？

### Q3. 旧收藏的「已入手」如何认定？

建议：V5 现有 `collections` 迁移为 `status=owned`，`received_at` 留空，不伪造日期；新记录要把状态改为 owned 才算拥有。
确认：旧数据不要求补收货日期，对吗？

### Q4. 多副本价格是否需要精确到每一本？

建议：先用 `quantity + 订单行`；如果每一本都要独立成本，P3 加 `book_copies`。
请选择：A 一卷一行（推荐）/ B 每本一行。

### Q5. 报告是否需要精确「本月新增已拥有」？

建议：增加 `status_history`，状态变更时追加；否则月报只能用当前状态/购买日期近似。
请选择：A 加 history（推荐，+1–2 人天）/ B 近似。

### Q6. 软删除保留多久？

建议：默认永久保留，回收站手动永久删除；备份包含软删除记录。
请选择：A 永久保留（推荐）/ B 30 天后自动清理。

### Q7. 自定义徽章规则复杂度？

建议：先支持固定规则类型（数量/系列/角色/套书/月度/年度/手动），不做任意脚本。
确认：这样可以吗？如果要做「任意组合条件」，P5 会增加 3–5 人天。

### Q8. 备份是否默认包含回收站？

建议：默认包含；恢复后仍在回收站。
确认：可以吗？
