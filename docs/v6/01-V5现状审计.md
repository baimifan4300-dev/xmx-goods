# 01 · V5 现状审计

> 审计对象：`output/xmx-goods-v5`（V5 源码）与线上 Supabase 项目 `lcwdgtbzeifqvsyewgpe`。
> 代码基线：GitHub `main` / `85c2600`；网站版本 `5.0.0`；数据结构 `2026-11-supabase-v1`；备份格式 v2。
> 审计方式：逐文件读取 + Migration 对照 + Supabase REST 实际读取公开参考表。
> 结论日期：2026-11-24。

## 1. 结论摘要

V5 是一个可运行的**单用户云端谷子图鉴**，不是通用收藏系统：

- 前端是原生 HTML/CSS/JS，`src/main.js` 一个 2608 行主模块，esbuild 打包为 `app.js`；
- Supabase 承担 Auth、PostgreSQL、Storage、Realtime；
- 商品固定是「谷子」语义：`products.work_id / character_id / main_category_key / board_key`；
- 作品/角色是只读种子数据，前端没有 CRUD；
- 20 个主分类是全局只读，前端不能改名、排序、增删；
- 收藏只有「已拥有 / 愿望」两种隐式状态，没有可配置状态；
- 图片只有 `cover / highres` 两种 kind，一图一记录，不是多图相册；
- 备份是 v2，覆盖 V5 表，但没有书籍、状态、付款、字段、成就、相册等 V6 数据。

V6 的新功能不能在现有 `products` 表上硬塞，否则会破坏 1537 条商品的结构和 V5 兼容性。

## 4. V5 已有功能清单

### 4.1 账号与启动

- Supabase Auth 邮箱 + 密码登录/注册、找回密码、重发确认；
- `config.js` 运行时配置，`validateSupabaseConfig` 拒绝 `service_role` / `sb_secret_`；
- `?demo=1` 才进入本地预览，否则云端为权威源；
- 首次登录云端为空时自动导入 1537 条 + V4 本机收藏/分类；
- `onAuthChange` 处理 `SIGNED_OUT` / `PASSWORD_RECOVERY`。

代码：`src/main.js` 71–140、458–585；`src/cloud-supabase.js` 48–118。

### 4.2 首页

- 4 个统计卡：图鉴商品、已拥有、愿望、收集率；
- 作品/角色条 `#worksStrip` 由 `store.works` 渲染；
- 快速入口、联动/满赠入口；
- 作品/角色**只用于展示和路由主题**，没有管理按钮。

代码：`src/main.js` 614–657；`index.html` 50–97。

### 4.3 全图鉴

- 搜索 `name/series/productCode/notes/folder/variety/mainCategory/board/classificationBasis/marketPrice`；
- 筛选：主分类、板块、待核对、已拥有/愿望/未收藏；
- 排序：名称/最近添加/价格/市场价；
- 分页 `PAGE_SIZE=60`；
- 卡片、详情弹窗、合集图红框定位、高清图优先；
- **没有按 `work_id / character_id` 过滤**：切换角色只改主题，商品列表不变。

代码：`src/main.js` 727–819、924–976、1301–1408。

### 4.4 商品管理

- 站内新增/编辑/删除；
- 字段：名称、作品、角色、主分类、独立板块、联动/满赠子分类、品种、版本、发售日期、市场价、编号、系列、备注；
- 原始商品删除需要二次确认并输入「删除」；
- 删除会级联删除收藏、愿望、分类归属、图片记录；
- `revision` 乐观锁 + 冲突弹窗（保留云端/覆盖）。

代码：`src/main.js` 1454–1838；`src/cloud-supabase.js` 192–233。

### 4.5 收藏 / 愿望

- `collections`：数量、实际购买价、购买日期、备注；
- `wishlist`：只有 `(owner, product_id)`，没有目标价、链接、店铺、到货日期、状态；
- 收藏/愿望互斥：加入收藏会删除愿望；
- 没有「未拥有 / 想要 / 已预订 / 待补尾款 / 已取消」状态。

代码：`src/main.js` 1150–1260；Migration 84–109。

### 4.6 分类

- 20 个主分类：`main_categories` 全局 seed，前端只读；
- 联动/满赠：`board_categories` + `board_assignments`，支持新建/重命名/删除/归类；
- 删除联动/满赠分类会把商品转为「未分类」，不删商品；
- 主分类不能改名、排序、新增、删除。

代码：`src/main.js` 982–1144；Migration 111–145。

### 4.7 图片

- 私有桶 `product-images`；
- 路径 `${userId}/${productId}/${kind}-${timestamp}.${ext}`；
- kind 只有 `cover` / `highres`，唯一 `(owner, product, kind)`；
- 上传压缩到 2400px、质量 0.9，生成 640px WebP；
- 删除高清图回退到原始合集图；
- 没有多图相册、没有图片说明/排序/主图切换。

代码：`src/main.js` 1840–1972；`src/images.js` 80–118；Migration 147–170、202–232。

### 4.8 备份 / 恢复

- ZIP：`data.json` + `manifest.json` + `images/uploads` + `images/base`；
- 格式 `xmx-goods-backup` v2；
- 恢复前校验 manifest、图片存在、SHA-256；
- 合并/覆盖两种模式；恢复前二次确认；
- 但不包含书籍、状态、付款、字段、成就、相册、地点等 V6 数据。

代码：`src/backup.js` 31–455；`src/main.js` 2243–2400。

## 5. 实际数据库结构

### 5.1 表清单

| 表 | 主键 | 关键约束 |
|---|---|---|
| `profiles` | `id` | FK auth.users，RLS 本人 |
| `works` | `id` | 公开只读；无 owner/revision |
| `characters` | `(work_id,id)` | FK works；公开只读 |
| `main_categories` | `key` | 全局 20 行；`sort_order` unique；公开只读 |
| `products` | `(owner_id,id)` | FK characters；board_key 只允许 collab/gift；`payload` 全字段 |
| `collections` | `(owner_id,product_id)` | FK products；quantity>=1；`purchase_price` |
| `wishlist` | `(owner_id,product_id)` | FK products；无其他字段 |
| `board_categories` | `(owner_id,id)` | FK characters；board_key 只允许 collab/gift；名称 1–20 |
| `board_assignments` | `(owner_id,product_id,board_key)` | FK product/category；触发器校验同板块 |
| `product_images` | `id` | FK products；kind 只允许 cover/highres；唯一 `(owner,product,kind)` |
| `user_settings` | `owner_id` | `settings jsonb` |
| `backup_logs` | `id` | 导出记录，`format_version=2` |

### 5.2 触发器

- `handle_new_user`：auth.users 插入后建 profiles + user_settings；
- `bump_revision`：products/collections/wishlist/board_categories/board_assignments/product_images/user_settings 更新时 `revision=old+1`；
- `set_updated_at`：profiles；
- `validate_board_assignment`：商品与分类必须同板块。

### 5.3 索引

已有：`products(owner_id,board_key)`、`products(owner_id,main_category_key)`、`products(owner_id,updated_at)`、`collections(owner_id)`、`wishlist(owner_id)`、`board_categories(owner_id,board_key,sort_order)`、`board_assignments(owner_id,category_id)`、`product_images(owner_id,product_id)`、`backup_logs(owner_id,created_at)`。

## 7. V5 → V6 的核心缺口

| V6 能力 | V5 现状 | 缺口 |
|---|---|---|
| 双收藏类型 | 只有谷子 | 无 `collection_types`；无书籍表 |
| 作品/角色 CRUD | 只读 seed | 无 owner/写策略/编辑 UI |
| 主分类管理 | 全局只读 20 条 | 无自定义分类、无改名/排序覆盖 |
| 真角色筛选 | 只换主题 | `filteredProducts()` 未按 work/char 过滤 |
| 状态系统 | 只有 owned/wish 隐式状态 | 无 `status_definitions`，collections 无 status |
| 预订/尾款 | 只在备注里 | 无 orders/payment_records |
| 系列清单 | `products.series` 文本，无清单 | 无 series/series_items |
| 书籍套/卷 | 无 | 无 book_sets/books |
| 自定义字段 | 无 | 无 field_definitions/field_values |
| 价格历史 | 只有当前 market_price | 无 price_history / market_price_date |
| 成就徽章 | 无 | 无 achievements/user_achievements |
| 多图相册 | 只有 cover/highres | 无 item_images |
| 收藏地点 | 无 | 无 locations |
| 出物 | 无 | 无 sales |
| 重复检测 | 只有 `duplicate_group` 文本 | 无检测结果/确认表 |
| 软删除/回收站 | 直接 DELETE | 无 deleted_at/is_deleted |
| 备份 v4 | v2，只覆盖 V5 | 缺全部 V6 数据 |

## 8. 兼容性硬约束

1. `products.id` 是原始 ID（如 `B01-001`）或站内新增 `U-...`；不能重编号。
2. `products.work_id/character_id` 外键到 `characters(work_id,id)`；新增角色必须走同一组合键。
3. `products.main_category_key` 不是外键；自定义分类可以存在，但删除时必须先重归类。
4. `board_key` 只有 `collab/gift`；V6 若新增板块，需要另开表，不能改这个 check。
5. `collections` 与 `wishlist` 的 FK 都是 `(owner_id, product_id)`；书籍不能塞进 `collections.product_id`，否则会破坏外键。
6. `product_images.kind` 只有 `cover/highres`；多图相册必须新表，不能直接扩 kind 后破坏旧唯一键。
7. 备份 v2 恢复逻辑只认识 `products/collections/wishlist/boardCategories/boardAssignments/productImages/settings`；V6 必须保留 v2 读取分支。
8. 1537 条原始商品中 435 条没有主分类、1527 条没有系列；V6 迁移不能假设每条都有分类/系列。

## 9. 审计限制

- 没有直接读取 `products` 等私有表的线上行数；需要你的登录态或 SQL Editor。
- 没有读取 `storage.objects` 的实际文件清单；只确认了桶策略/路径设计。
- 没有执行任何数据库 Migration；本文所有表结构是「现有实际结构 + 计划新增」，不是已存在的表。
- 线上 `main_categories/works/characters` 已实际读取；其余以 Migration 文件为准。

## 10. 审计结论

V5 可以作为 V6 的稳定底座，但必须遵守：

- **保留 `products` 原表**，书籍另建表；
- **保留 20 主分类原表**，自定义分类另建表；
- **保留 `product_images`**，多图相册另建 `item_images`；
- **保留 `wishlist` 兼容**，V6 用 `collections.status_id` 统一状态；
- **所有删除先软删除**，回收站再永久删除；
- **备份 v4 必须能读 v2**。
